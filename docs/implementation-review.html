OpenCompare earns its strongest marks for turning a comparison into a verifiable result. A user can resolve one conflicting edit, keep an independent change from the other file, and export both in the same document. What drives the scores

TypeScript

92%

Strict TypeScript fits a tool where choosing the wrong side can overwrite work. The merge engine limits conflict choices to ours, theirs, base, or both. A shared platform interface lets the desktop and browser implementations expose the same file operations, and the comparison algorithms can run directly in Node tests.

One missed opportunity sits in the merge model itself. A block declares its kind and nullable source separately, so the type admits a stable block with no source. Encoding stable and conflicting blocks as distinct types would let the compiler enforce the rule already written in the comments.

Compiler settings · Merge model · Platform interface

Electron, React and Vite

86%

Electron gives the workbench real filesystem access and native dialogs. The renderer reaches those capabilities through a preload bridge, with context isolation enabled. React and virtualized rows suit two panes that must keep large lists aligned. Playwright can drive the compiled window and verify the resulting file on disk.

The cost is visible on large workloads. A recorded comparison of 358,249 directory entries peaked at 855.5 MiB of renderer memory and 1,310.4 MiB for the app. That historical result gives maintainers a concrete reason to profile large trees. It includes the comparison data and does not isolate Electron’s contribution.

Comparison and merge

84%

The folder workflow connects discovery to action. Users can filter one-sided entries, drill into a changed file, preview a sync, and explicitly select deletions in mirror mode. CSV key matching and JSON/YAML path comparison also give useful answers when rows or keys move. Snapshots support later comparisons against a recorded directory.

Depth varies by format. Directory hashing detects a changed binary, but the file view offers no byte-level drilldown. XLSX comparison reads workbook data and leaves formulas unevaluated, and older XLS files are outside its supported formats. Folder comparisons pick up external edits on the next scan.

Desktop workbench

78%

Aligned panes reduce the work of matching lines by eye. Inline highlights identify which characters changed, and folder rows pair color with labels such as “Right only.” In the compiled app, keyboard navigation brought an off-screen difference into view on both sides. Scrolling the left pane kept the right pane aligned.

Action discovery costs points. On a folder row, a click selects the item and a double-click opens a file. Right-clicking a row offers no app-specific commands. In the file view, similar arrow and disk icons sit above both panes, so users must establish the target side before acting. A row menu with named, side-specific actions would address the interaction gap you encountered.

LeeCompare

Design proposal for a desktop comparison and merge tool

Build LeeCompare around a question that matters before every write: which files will change, why, and what happens if the operation stops halfway? Put that answer in the workbench, make it available to scripts, and test it against the files actually left on disk.

I would build LeeCompare with Rust for the engine and C++ with wxWidgets for the desktop UI. A comparison tool spends much of its time in trees, menus and file pickers. Native controls fit that work, and the wxWindows Library Licence’s binary exception permits commercial application binaries under the application developer’s own terms. Qt also offers a commercial-use route under the LGPL for eligible modules, subject to its terms. The deciding factors here are the wxWidgets binary exception and the fit of its native controls. wxWidgets licence · Qt’s LGPL guidance

Budget for a Rust and C++ team and interactive test runners on three operating systems. The proposed GUI and test stack requires no purchased GUI toolkit or GUI-test-runner licence. LeeCompare’s performance and usability targets still require a working build and comparative measurements.

The stack I would ship

Language and engine
Use Rust for file traversal, byte and text comparison, three-way merge, and sync execution. Keep paths, file identities, and decoded display strings distinct. Pass bounded batches of rows to the UI, preserve the original encoding and line endings, and page large inputs. Rust’s ownership model fits these long-lived buffers. The cost is a second language at the UI boundary, so keep the CXX interface small and versioned. Rust ownership · CXX bridge
Desktop workbench
Use wxWidgets menus, file dialogs and a model-backed directory view. Keep selection keyed by file identity as sorted or filtered rows move. The toolbar, context menu, keyboard shortcut and command search should pass the same selected side and file ID to the same command. Prototype the custom diff pane first on all three systems. An OS accessibility client must be able to read a changed line, tell left from right, move focus to the next change and invoke its action. That is the acceptance test for a custom-drawn control. wxWidgets platform overview
Storage and recovery
Use SQLite for session state and a durable operation journal. Build an immutable plan from the selected roots. Immediately before writing, recheck file identity and content against the preview. On local disk, stage replacements on the destination volume, retain the prior version, and record each completed step. Recovery must reconcile the journal with disk state after a crash. A database transaction alone cannot undo an external file write. SQLite commit model
CLI and integrations
Ship a Rust CLI over the same engine. A CI job could compare two trees, export a versioned JSON plan, and apply that exact plan subject to the same checks as the GUI. Support Git diff and merge tool invocation. Give each storage connector explicit capabilities for rename, conditional writes and recovery, so an SFTP or object-store preview can state precisely what it guarantees.

What the workbench should feel like

Open two roots and land on the first difference. Each tree row shows a filename, a word such as “Modified” and its side. Right-click settings.yaml on the right and choose Compare contents, Copy path, or Stage right → left. The menu names the destination. Shift+F10 opens the same commands from the keyboard, and Escape returns focus to that row. Staging adds a line to a review pane with both paths and the expected change. An intervening edit marks that line stale and requires a fresh decision.

For a three-way conflict, show base, ours and theirs above an editable result. Link every unresolved block to its source lines and show the exact output diff before saving. Two-way work should keep two panes. When a user returns from a file to its folder, restore the tree selection, filter and scroll position. Labels, patterns and high-contrast themes should make every change readable independently of color.

Feature priorities against both rivals

  1. First release · trusted local merge. Deliver text and byte comparison, two- and three-way folder reconciliation, editable merge output, snapshots and resumable sync. Combine Beyond Compare’s folder merge depth with OpenCompare’s explicit deletion preview. Preserve ambiguous rename matches as user decisions. Offer a separately reviewable plan for automation.
  2. Next · explain structured changes. Let users switch between raw text and semantic edits for JSON, YAML, CSV and XLSX. Each difference should identify its source location, row key or sheet and cell. Surface duplicate keys, missing formula caches, and changes hidden by normalization. A saved report should record the comparison rules so another reviewer can reproduce it.
  3. Then · broaden desktop coverage. Add image overlays and pixel differences, archive browsing, SFTP and S3. Start connectors read-only. Enable writes once interruption and recovery tests pass for that connector. These features close concrete gaps with Beyond Compare while the local release remains useful on its own.

How LeeCompare would earn the comparison

Publish a versioned corpus with known answers: a 100,000-entry tree containing renames and one-sided files, a mixed-ending text merge, a workbook with duplicate keys, and an interrupted sync. Run all three products against identical local copies on the same hardware. Record product versions, settings, OS, storage, and cache state. Report unsupported workflows separately. Count a completed task only after its output matches the expected result.

Proposed acceptance targets. On a published reference machine, aim for a first navigable result within two seconds on the 100,000-entry cold scan and cancellation acknowledgment within 250 ms at the 95th percentile. Measure completion time separately, alongside peak memory for the full process tree. Run 30 repetitions per tool and cache condition. For usability, counterbalance tool order and measure completion time and wrong-target actions on the same file and folder tasks. Claim a lead only for a measured workload with equivalent output. A silent overwrite or unexplained divergence from the preview blocks release regardless of speed.
